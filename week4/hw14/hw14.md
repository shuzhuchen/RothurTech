## what is index
An index is a special data structure that helps the database find data much faster without scanning every row in a table. 

The main benefit of an index is improved query performance, especially for columns used in WHERE, JOIN, ORDER BY, and GROUP BY clauses. However, indexes also have a cost because the database must maintain them during INSERT, UPDATE, and DELETE operations, which can slow down write performance.

## clustered index vs nonclustered index
A clustered index determines the physical order of data stored in a table. Because the data can only be stored in one order, each table can have only one clustered index. In most databases, the primary key is implemented as a clustered index.

A non-clustered index is a separate structure that stores indexed values along with pointers to the actual rows. A table can have multiple non-clustered indexes on different columns to improve search performance.

## data structure for index
The most common data structure used for database indexes is the B+ Tree. B+ Trees provide O(log n) search performance and are very efficient for both exact lookups and range queries.

Some databases also support Hash Indexes for fast equality searches, Bitmap Indexes for analytical workloads, and R-Trees for geospatial data. However, B+ Trees are the most widely used index structure in relational databases.

## view vs store procedure
A view is a virtual table created from a SQL query. It does not store data itself and executes the underlying query whenever it is accessed. Views are mainly used to simplify complex queries and restrict access to certain data.

A stored procedure is a collection of SQL statements and business logic stored inside the database. It can contain conditions, loops, variables, and data modification statements. Stored procedures are commonly used to encapsulate complex business processes and reduce communication between the application and the database.

## view vs material view
A standard view only stores the SQL definition and executes the query every time it is accessed. This ensures that the data is always up to date, but performance may be slower for complex queries.

A materialized view physically stores the query results on disk. Since the results are precomputed, query performance is much faster. However, the data may become stale and must be refreshed periodically to stay synchronized with the source tables.

## how to tune the sql query
When tuning SQL queries, the first step is usually to analyze the execution plan using EXPLAIN to identify bottlenecks. Common optimization techniques include creating proper indexes, avoiding SELECT *, reducing unnecessary data retrieval, optimizing joins, implementing pagination for large datasets, and replacing expensive subqueries with window functions when appropriate. The overall goal is to reduce full table scans, minimize I/O operations, and improve query execution efficiency.

## Saga vs 2PC
Both Saga and Two-Phase Commit (2PC) are approaches for handling distributed transactions in microservice architectures.

2PC uses a central coordinator to ensure that all participating services either commit or roll back together. It provides strong consistency but can introduce blocking, resource locking, and performance bottlenecks.

Saga breaks a distributed transaction into multiple local transactions. If one step fails, compensating transactions are executed to undo previous operations. Saga offers better scalability and performance because it avoids distributed locks, but it provides eventual consistency rather than strong consistency.

In modern microservice systems, Saga is generally preferred because it scales better and avoids the limitations of distributed locking.

## what are the use case for the following design pattern in Banking, E-Commerce and Health Insurance Industry (Total 12 use cases, recommend to do some research): singleton, factory, builder, proxy

Singleton ensures one instance with global access; Factory Method creates objects through an interface while subclasses or logic decide the concrete type; Builder constructs complex objects step by step; Proxy controls access to another object, often for security, lazy loading, caching, or remote access.

### Banking
1. Singleton: Central configuration manager for interest rates, fraud thresholds, feature flags, or bank-wide compliance settings. Only one shared config instance should be used across services to avoid inconsistent rules.

2. Factory: Payment processor factory creates different payment handlers: wire transfer, ACH, credit card, check deposit, or internal transfer. The service asks the factory for the correct processor based on transaction type.

3. Builder: Loan application builder creates a complex loan object step by step: applicant info, credit score, collateral, income, risk profile, documents, and approval terms. Useful because not every loan has the same required fields.

4. Proxy: Account access proxy checks authentication, authorization, fraud risk, and audit logging before allowing access to sensitive account or transaction data.

### E-Commerce
1. Singleton: Inventory cache manager or application-level configuration manager for tax rules, shipping rules, or promotion settings. The system uses one shared instance to avoid duplicated configuration loading.

2. Factory: Payment method factory creates handlers for credit card, PayPal, Apple Pay, gift card, or BNPL. Checkout logic does not need to know the exact implementation class.

3. Builder: Order builder creates a complex order with customer info, items, discounts, tax, shipping address, payment method, gift wrapping, and promotion codes. This keeps object construction cleaner than a long constructor.

4. Proxy: Product image or recommendation proxy lazily loads expensive product images/recommendations, caches results, or controls access to supplier inventory APIs.

### Health Insurance
1. Singleton: Eligibility rule configuration manager for claim limits, plan rules, provider network settings, or compliance parameters. One shared instance helps keep rule access consistent.

2. Factory: Claim processor factory creates different processors for dental, vision, pharmacy, outpatient, or emergency claims. Each claim type can have different validation and calculation rules.

3. Builder: Insurance policy builder creates a policy object with member info, dependents, plan type, deductible, copay, coverage details, exclusions, and effective dates. Useful because plans can vary a lot.

4. Proxy: Medical record / claim access proxy checks HIPAA-style access control, masks sensitive data, logs access, and only then forwards the request to the real claim or patient record service.

## what is microservice architecture
Microservice architecture is an approach to building a distributed system by slicing a large, monolithic application into smaller, independent Java applications based on their specific business scope (for example, splitting an e-commerce platform into separate Product Management, Payment, and Shipment services). Instead of running all logic inside a single JVM memory model, each service runs on its own server instance and communicates with other services over the network, typically using RESTful HTTP endpoints.

## why microservice architecture
The industry shifted to microservices to handle exponentially increasing traffic that a single server simply cannot endure.

Pros:

1. High Availability and Failure Tolerance: If one module (like the shipment service) crashes, it does not bring down the entire system; users can still browse products or make payments.

2. Horizontal Scaling Flexibility: I can deploy multiple instances of a specific service (like spinning up 10 instances of an "Order Service" during the Christmas holiday) to handle peak traffic, and then easily downscale (cancel the server rentals) when the season ends to save costs.

Cons (Trade-offs):

1. Communication Overhead: Moving from internal method calls within a single JVM to network calls between different servers introduces latency and potential network instability.

2. Producer/Consumer Bottlenecks: A fast upstream service might send requests faster than a downstream service can process them, leading to data loss or queues filling up.

3. Inconsistency and Complexity: Maintaining data consistency across dozens of separate databases is highly complex, as is traffic allocation and managing configurations for hundreds of service instances.

## microservice main components
To manage the trade-offs mentioned above, a microservice ecosystem requires a suite of auxiliary components working together as a cluster. These include API Gateways, Messaging Queues, Configuration Servers, Service Discovery registries, Load Balancers, and Monitoring/Tracing tools.

### Config Server: Config server
Config Server is used to centralize configuration for all microservices. In a microservice system, we may have many services and many environments, such as dev, QA, staging, and production. If every service stores its own database URL, API keys, feature flags, and timeout values locally, it becomes hard to manage.

With Config Server, services can fetch configuration from a central place during startup. This makes configuration easier to manage, version, and update.

```
@SpringBootApplication
@EnableConfigServer
public class ConfigServerApplication {
    public static void main(String[] args) {
        SpringApplication.run(ConfigServerApplication.class, args);
    }
}
```

client side:
```
spring:
  application:
    name: order-service
  config:
    import: optional:configserver:http://localhost:8888
```
    
### Service Discovery: Eureka, Consoul, Zookeeper...
Service Discovery is like a registration center for microservices. When a service instance starts, it registers its service name, IP address, and port with the discovery server. Other services do not need to hardcode the downstream service IP. They can ask the discovery server where the target service is.

Each instance usually sends heartbeat signals to prove it is still alive. If the discovery server stops receiving heartbeats, it can remove that instance from the registry.

example: Order Service starts
→ registers itself to Eureka
→ Payment Service wants to call Order Service
→ asks Eureka for available Order Service instances
→ calls one available instance

```
@SpringBootApplication
@EnableEurekaServer
public class EurekaServerApplication {
    public static void main(String[] args) {
        SpringApplication.run(EurekaServerApplication.class, args);
    }
}
```
client side:
```
spring:
  application:
    name: order-service

eureka:
  client:
    service-url:
      defaultZone: http://localhost:8761/eureka/
```
### Zipkin and Sleuth: tracing system
Distributed tracing is used to track one request across multiple microservices. In a monolithic application, debugging is easier because logs are inside one application. But in microservices, one user request may go through API Gateway, Order Service, Payment Service, and Inventory Service.

Tracing tools attach a trace ID to the request. This trace ID travels across services, so we can search logs by trace ID and understand the full request path.

example: Request Trace ID: abc-123

API Gateway
→ Order Service
→ Payment Service
→ Inventory Service

```
<dependency>
    <groupId>io.micrometer</groupId>
    <artifactId>micrometer-tracing-bridge-brave</artifactId>
</dependency>

<dependency>
    <groupId>io.zipkin.reporter2</groupId>
    <artifactId>zipkin-reporter-brave</artifactId>
</dependency>
```
    
### Ribbon: client side load balancer
Ribbon is a client-side load balancer. When one service wants to call another service, and the target service has multiple instances, Ribbon helps choose which instance to call.

For example, if Order Service has three instances, Ribbon can use round-robin strategy to distribute requests across instance 1, instance 2, and instance 3.

example: Payment Service wants to call Order Service

Order Service instances:
- order-service-1
- order-service-2
- order-service-3

Ribbon chooses one instance, for example using round-robin.

```
@Bean
@LoadBalanced
public RestTemplate restTemplate() {
    return new RestTemplate();
}
```
Then call by service name:

```
restTemplate.getForObject("http://order-service/orders/1", OrderDto.class);
```


### ELK: kibana, Logstash, ElasticSearch
ELK is used for centralized logging.

Logstash collects and processes logs from different microservices. Elasticsearch stores and indexes those logs so we can search them quickly. Kibana provides a dashboard to visualize and search logs.

In microservices, logs are distributed across many services and machines. Without centralized logging, debugging is very hard. With ELK, we can search by trace ID, user ID, service name, error message, or timestamp.

example log:
```
{
  "traceId": "abc-123",
  "service": "payment-service",
  "level": "ERROR",
  "message": "Payment provider timeout"
}
```

### Circuit Breaker: fall back
Circuit Breaker is a fault-tolerance pattern. It prevents cascading failure when a downstream service is slow or unavailable.

For example, if Order Service calls Payment Service, but Payment Service is down, Order Service should not keep waiting forever or retry infinitely. The circuit breaker can stop calling Payment Service temporarily and return a fallback response, such as cached data or a friendly error message.

it has 3 states: 1. Closed: normal calls are allowed. 2. Open: downstream is failing, calls are blocked and fallback is returned. 3. Half-open: allow a few test calls to see if downstream recovered

```
@CircuitBreaker(name = "paymentService", fallbackMethod = "paymentFallback")
public String processPayment() {
    return restTemplate.getForObject(
            "http://payment-service/pay",
            String.class
    );
}

public String paymentFallback(Exception ex) {
    return "Payment service is temporarily unavailable. Please try again later.";
}
```

### Hystrix -> Resilience4j
Hystrix was the older Netflix circuit breaker library. In many older Spring Cloud projects, people used Hystrix for circuit breaker, fallback, and fault tolerance.

But Hystrix is no longer the preferred modern choice. In newer Spring Boot and Spring Cloud projects, Resilience4j is more commonly used. Resilience4j supports circuit breaker, retry, rate limiter, bulkhead, and time limiter patterns.

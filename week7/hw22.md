### point to point vs publish subscribe model, pros and cons for each

**Point-to-point model** means one message is consumed by only one consumer. The producer sends a message to a queue, and one consumer from the consumer pool processes it.

Example: order service sends a payment task to a queue, and only one payment worker handles that order.

**Pros:**

* Simple design.
* Good for task distribution.
* Avoids duplicate processing because only one consumer handles each message.
* Easy to scale consumers horizontally.

**Cons:**

* Not suitable when multiple systems need the same message.
* Once a message is consumed, other consumers cannot process it.
* Less flexible for event-driven systems.

**Publish-subscribe model** means one message can be delivered to multiple subscribers. The producer publishes an event to a topic, and every subscribed consumer group can receive a copy.

Example: an `OrderCreated` event can be consumed by inventory service, payment service, notification service, and analytics service.

**Pros:**

* Good for event-driven architecture.
* One event can trigger multiple downstream services.
* Producer and consumers are loosely coupled.
* Easy to add new consumers without changing the producer.

**Cons:**

* More complex than point-to-point.
* Possible duplicate processing if consumers are not idempotent.
* Harder to debug because many services may react to the same event.
* Message ordering and delivery guarantees need careful design.

In Kafka, the publish-subscribe model is implemented using **topics** and **consumer groups**. Consumers in the same group share messages, while different consumer groups each receive their own copy of the messages.

### why message system

A message system is used to decouple services and improve scalability, reliability, and fault tolerance.

Without a message system, services usually call each other synchronously. If one downstream service is slow or unavailable, the upstream service may also fail or become slow.

With a message system like Kafka, the producer only sends the message to Kafka. The consumer can process it later at its own speed.

Main reasons to use a message system:

1. **Decoupling**

   * Producer does not need to know who consumes the message.
   * New consumers can be added without changing producer code.

2. **Asynchronous processing**

   * The producer does not need to wait for the consumer to finish.
   * This improves response time for user-facing APIs.

3. **Traffic buffering**

   * Kafka can absorb traffic spikes.
   * Consumers can process messages gradually.

4. **Scalability**

   * We can scale producers and consumers independently.
   * More consumers can be added in a consumer group to increase processing throughput.

5. **Reliability**

   * Messages are persisted in Kafka.
   * If a consumer crashes, it can resume from the last committed offset.

6. **Event-driven architecture**

   * Services can communicate through business events like `OrderCreated`, `PaymentCompleted`, or `UserRegistered`.


### kafka architecture

Kafka architecture is mainly made of producers, brokers, topics, partitions, consumers, consumer groups, offsets, and ZooKeeper or KRaft metadata management.

**Producer**

* Sends messages to Kafka topics.
* Can choose which partition to send to by key.
* For example, if the key is `userId`, all messages for the same user can go to the same partition to preserve ordering.

**Broker**

* A Kafka server.
* A Kafka cluster usually has multiple brokers.
* Brokers store topic partitions and serve producer and consumer requests.

**Topic**

* A logical category for messages.
* Example: `order-events`, `payment-events`, `user-events`.

**Partition**

* A topic is split into partitions.
* Partitions allow Kafka to scale horizontally.
* Ordering is guaranteed only within a single partition, not across the whole topic.

**Replica**

* Each partition can have replicas on multiple brokers.
* Replication provides fault tolerance.

**Leader and followers**

* For each partition, one broker is the leader.
* Producers and consumers talk to the leader.
* Followers replicate data from the leader.
* If the leader fails, one follower can be elected as the new leader.

**Consumer**

* Reads messages from Kafka topics.
* Consumers pull data from Kafka instead of Kafka pushing data to them.

**Consumer group**

* A group of consumers that work together.
* Each partition is consumed by only one consumer within the same consumer group.
* Different consumer groups can consume the same topic independently.

**Offset**

* The position of a message inside a partition.
* Kafka does not track “message consumed” directly. Instead, consumers commit offsets.
* If a consumer fails, it can restart from the last committed offset.

**Controller / metadata management**

* Older Kafka versions used ZooKeeper.
* Newer Kafka versions can use KRaft mode, where Kafka manages metadata internally without ZooKeeper.

A simple flow is:

```text
Producer -> Topic -> Partition -> Broker -> Consumer Group -> Consumer
```


### message accumulated in Kafka, consumer can't consume all the data on time, what should you do?

If messages are accumulating in Kafka, it means consumer lag is increasing. I would handle it step by step.

First, I would identify the bottleneck:

* Check consumer lag.
* Check consumer processing time.
* Check CPU, memory, database, network, and downstream API latency.
* Check whether the consumer is blocked by slow external calls.

Then I would improve the consumer side:

1. **Scale consumers horizontally**

   * Add more consumer instances in the same consumer group.
   * This only helps if the topic has enough partitions.
   * Maximum parallelism in one consumer group is limited by the number of partitions.

2. **Increase partition count**

   * If there are fewer partitions than consumers, add more partitions.
   * More partitions allow more consumers to process in parallel.
   * Need to be careful because increasing partitions can affect key-based ordering.

3. **Optimize consumer processing logic**

   * Reduce slow database queries.
   * Use batch processing.
   * Use connection pooling.
   * Avoid unnecessary synchronous calls.
   * Cache repeated lookups where appropriate.

4. **Increase batch size**

   * Tune consumer configs like `max.poll.records`, `fetch.min.bytes`, and `fetch.max.wait.ms`.
   * Batch processing can improve throughput.

5. **Make processing asynchronous**

   * If each message requires slow I/O, use async processing or worker pools carefully.
   * Still need to manage offset commits safely.

6. **Check downstream systems**

   * If the consumer writes to a database or calls another API, that downstream system may be the real bottleneck.
   * Scale or optimize the downstream system.

7. **Use backpressure**

   * If consumers cannot keep up, slow down producers if possible.
   * This prevents unlimited lag growth.

8. **Separate hot traffic**

   * If one type of message is much heavier, split it into a separate topic.
   * This prevents heavy messages from blocking normal messages.

9. **Handle poison messages**

   * A bad message may repeatedly fail and block progress.
   * Use retry topics and dead-letter topics.


### How does Kafka deal with the expired data?

Kafka handles expired data using **retention policies**.

Kafka does not delete a message immediately after it is consumed. Instead, Kafka keeps messages based on topic-level retention configuration.

There are two common retention strategies:

1. **Time-based retention**

   * Messages are deleted after a configured time.
   * Example: keep messages for 7 days.

```properties
retention.ms=604800000
```

2. **Size-based retention**

   * Kafka deletes old log segments when the topic reaches a configured size limit.

```properties
retention.bytes=1073741824
```

Kafka stores messages in log segments. When a segment becomes older than the retention time or the topic exceeds the retention size, Kafka deletes old segments.

Kafka also supports **log compaction**.

With log compaction, Kafka keeps the latest value for each key instead of simply deleting data by time. This is useful for changelog-style topics.

Example:

```text
user-1 -> name=A
user-1 -> name=B
user-1 -> name=C
```

After compaction, Kafka may keep only the latest value:

```text
user-1 -> name=C
```

So Kafka deals with expired data by deleting old log segments based on retention time or retention size, or by compacting records based on key.

### data volume in Kafka?

Kafka can handle very large data volume because it is distributed, partitioned, sequential-write based, and horizontally scalable.

When we talk about Kafka data volume, I usually consider:

1. **Message size**

   * Average size of each message.
   * Example: 1 KB per message.

2. **Message rate**

   * Number of messages per second.
   * Example: 50,000 messages per second.

3. **Retention period**

   * How long Kafka needs to keep messages.
   * Example: 7 days.

4. **Replication factor**

   * How many copies Kafka stores.
   * Example: replication factor 3.

5. **Compression**

   * Compression like `lz4`, `snappy`, or `zstd` can reduce storage and network usage.

A basic storage calculation is:

```text
Storage = message_size * messages_per_second * seconds_retained * replication_factor
```

Example:

```text
message size = 1 KB
message rate = 10,000 messages/sec
retention = 7 days
replication factor = 3

storage = 1 KB * 10,000 * 604,800 * 3
        = about 18 TB before compression
```

In production, I would also include extra disk capacity for index files, segment overhead, traffic spikes, rebalancing, and future growth.

For Kafka throughput, I would monitor:

* Bytes in per second.
* Bytes out per second.
* Messages in per second.
* Consumer lag.
* Broker disk usage.
* Network I/O.
* Request latency.


### How to calculate partition number?

Partition number depends on throughput, parallelism, ordering requirements, and future growth.

I usually calculate it from both producer throughput and consumer throughput.

Formula:

```text
partitions >= max(
  target_producer_throughput / throughput_per_partition_producer,
  target_consumer_throughput / throughput_per_partition_consumer
)
```

Example:

```text
Target producer throughput = 100 MB/s
Each partition can handle 10 MB/s producer throughput
Producer requirement = 100 / 10 = 10 partitions

Target consumer throughput = 100 MB/s
Each partition can handle 5 MB/s consumer throughput
Consumer requirement = 100 / 5 = 20 partitions

Final partition count should be at least 20
```

Other factors:

1. **Consumer parallelism**

   * In one consumer group, one partition can only be consumed by one consumer at a time.
   * If I need 20 consumers working in parallel, I need at least 20 partitions.

2. **Ordering**

   * Kafka only guarantees ordering within one partition.
   * If strict ordering is required for a key, all messages with that key must go to the same partition.
   * More partitions may reduce global ordering guarantees.

3. **Broker count**

   * Partitions should be distributed across brokers.
   * Too many partitions can increase metadata overhead, leader election time, memory usage, and recovery time.

4. **Future growth**

   * I usually choose a partition count that supports near-future traffic growth.
   * Increasing partitions later is possible, but it can change key-to-partition mapping and affect ordering.

I calculate partitions based on expected throughput and required consumer parallelism, then validate with load testing. I also consider ordering requirements and avoid creating too many partitions because partitions have operational overhead.

### AWS SQS vs rabbitMQ vs Kafka

**AWS SQS**

* Fully managed queue service from AWS.
* Good for simple decoupling, background jobs, and task queues.
* Supports standard queues and FIFO queues.
* Standard SQS provides high scalability but at-least-once delivery, so duplicate messages are possible.
* FIFO SQS supports ordering and exactly-once processing behavior within AWS limits.

**RabbitMQ**

* Traditional message broker.
* Supports queues, exchanges, routing keys, acknowledgments, and flexible routing patterns.
* Good for task queues, request/reply, routing-based messaging, and lower-latency message delivery.
* Messages are usually removed after being consumed.
* More broker-centric than Kafka.

**Kafka**

* Distributed event streaming platform.
* Messages are stored in topics for a configured retention period.
* Multiple consumer groups can read the same messages independently.
* Good for event-driven architecture, log aggregation, analytics pipelines, stream processing, and high-throughput systems.
* Kafka is not just a queue; it is a durable distributed commit log.

Comparison:

| Feature         | AWS SQS                             | RabbitMQ                        | Kafka                                      |
| --------------- | ----------------------------------- | ------------------------------- | ------------------------------------------ |
| Type            | Managed queue                       | Message broker                  | Event streaming platform                   |
| Message model   | Queue                               | Queue + pub/sub routing         | Distributed log                            |
| Management      | Fully managed by AWS                | Self-managed or managed service | Self-managed or managed service            |
| Retention       | Limited retention                   | Usually removed after ack       | Retained by time/size                      |
| Throughput      | High                                | Medium to high                  | Very high                                  |
| Ordering        | FIFO queue supports ordering        | Queue ordering possible         | Ordering within partition                  |
| Replay messages | Not the main use case               | Not the main use case           | Strong support                             |
| Consumer model  | Competing consumers                 | Competing consumers / routing   | Consumer groups                            |
| Best for        | Background jobs, simple async tasks | Complex routing, task queues    | Event streaming, analytics, event sourcing |

* Use **SQS** when I want a simple fully managed AWS queue.
* Use **RabbitMQ** when I need flexible routing and traditional broker features.
* Use **Kafka** when I need high-throughput event streaming, replayability, long retention, and multiple independent consumers.

### AWS SNS vs SQS

AWS SNS and AWS SQS solve different messaging problems.

**AWS SNS**

* Simple Notification Service.
* It is a publish-subscribe service.
* A producer publishes a message to an SNS topic.
* SNS pushes the message to multiple subscribers.
* Subscribers can be SQS queues, Lambda functions, HTTP endpoints, email, SMS, etc.

**AWS SQS**

* Simple Queue Service.
* It is a queue service.
* Producers send messages to a queue.
* Consumers poll the queue and process messages.
* A message is usually processed by one consumer.

Main difference:

```text
SNS = push-based pub/sub
SQS = pull-based queue
```

Comparison:

| Feature         | SNS                                                 | SQS                                         |
| --------------- | --------------------------------------------------- | ------------------------------------------- |
| Model           | Publish-subscribe                                   | Queue                                       |
| Delivery        | Push                                                | Pull                                        |
| Consumers       | Multiple subscribers receive copies                 | One consumer processes a message            |
| Message storage | Short-term delivery, not long-term queueing         | Stores messages until consumed or expired   |
| Use case        | Fan-out notifications                               | Background job processing                   |
| Example         | Notify email, Lambda, and SQS when order is created | Payment worker processes order payment task |

Common pattern: **SNS + SQS fan-out**

```text
Order Service -> SNS Topic -> SQS Queue A -> Inventory Service
                         -> SQS Queue B -> Notification Service
                         -> SQS Queue C -> Analytics Service
```

This pattern is useful because SNS broadcasts the event, while each SQS queue gives each service its own reliable buffer.

Use SNS when I need to broadcast an event to multiple subscribers. Use SQS when I need reliable queue-based asynchronous processing. Often, I use them together: SNS for fan-out and SQS for durable per-service processing.

## 1. How did you write unit tests and integration tests for your rewarding project?

In my project, I separated testing into different layers so each test had a clear purpose.

For **unit tests**, I focused on testing business logic in isolation. For example, in the service layer, I tested methods like reward calculation, name aggregation, validation rules, fallback logic, and exception handling. I used **JUnit 5** as the test framework and **Mockito** to mock dependencies such as repositories, downstream clients, or external services. The goal was to test the service behavior without starting the full Spring Boot application.

For example, for a service test, I would mock the repository, prepare input data, call the service method, and verify both the returned result and interactions with dependencies.

```java
@ExtendWith(MockitoExtension.class)
class RewardServiceImplTest {

    @Mock
    private RewardRepository rewardRepository;

    @InjectMocks
    private RewardServiceImpl rewardService;

    @Test
    void calculateReward_returnsCorrectPoints_whenPurchaseAmountIsValid() {
        RewardRequest request = new RewardRequest(120.00);

        RewardResponse response = rewardService.calculateReward(request);

        assertThat(response.getPoints()).isEqualTo(90);
    }

    @Test
    void calculateReward_throwsException_whenAmountIsNegative() {
        RewardRequest request = new RewardRequest(-10.00);

        assertThatThrownBy(() -> rewardService.calculateReward(request))
                .isInstanceOf(InvalidRewardRequestException.class);
    }
}
```

For **controller tests**, I used `@WebMvcTest` and `MockMvc`. This allowed me to test API endpoints, request validation, JSON serialization, HTTP status codes, and exception handling without loading the full application.

```java
@WebMvcTest(RewardController.class)
class RewardControllerTest {

    @Autowired
    private MockMvc mockMvc;

    @MockitoBean
    private RewardService rewardService;

    @Test
    void calculateReward_returns200_whenRequestIsValid() throws Exception {
        when(rewardService.calculateReward(any()))
                .thenReturn(new RewardResponse(90));

        mockMvc.perform(post("/api/rewards/calculate")
                        .contentType(MediaType.APPLICATION_JSON)
                        .content("""
                            {
                              "amount": 120.00
                            }
                        """))
                .andExpect(status().isOk())
                .andExpect(jsonPath("$.points").value(90));
    }
}
```

For **integration tests**, I used `@SpringBootTest` with a random port and sometimes RestAssured. These tests verified that the full flow worked end-to-end: HTTP request, controller, service, repository, database, and response. For database-related tests, I used an H2 test database or a test profile.

```java
@SpringBootTest(webEnvironment = SpringBootTest.WebEnvironment.RANDOM_PORT)
@ActiveProfiles("test")
class RewardIntegrationTest {

    @LocalServerPort
    private int port;

    @BeforeEach
    void setUp() {
        RestAssured.port = port;
    }

    @Test
    void calculateReward_returnsExpectedResult() {
        given()
            .contentType(ContentType.JSON)
            .body("""
                {
                  "amount": 120.00
                }
            """)
        .when()
            .post("/api/rewards/calculate")
        .then()
            .statusCode(200)
            .body("points", equalTo(90));
    }
}
```

I also integrated **JaCoCo** to enforce coverage and **SonarQube** in Jenkins to track coverage, code smells, bugs, and quality gates.

## 2. “TDD vs BDD vs DDD?”

**TDD**, or Test-Driven Development, is a development practice where we write the test before writing the implementation. The cycle is **Red, Green, Refactor**: first write a failing test, then write the minimum code to make it pass, then clean up the code. I use TDD when the business logic is clear and I want strong regression protection.

**BDD**, or Behavior-Driven Development, focuses on expected system behavior from the user or business perspective. It often uses language like “Given, When, Then.” BDD is useful when product owners, QA, and developers need a shared understanding of acceptance criteria.

For example:

```text
Given a customer has a purchase amount of $120
When the reward calculation runs
Then the customer should receive 90 reward points
```

**DDD**, or Domain-Driven Design, is more about software architecture and modeling complex business domains. In DDD, we design the system around domain concepts like entities, value objects, aggregates, repositories, and services. It helps keep business rules organized and prevents the application from becoming just database CRUD code.

In short:

```text
TDD = test-first development practice
BDD = behavior-focused collaboration and acceptance testing
DDD = domain-centered design and architecture
```

In real projects, they can work together. For example, I may use DDD to model the reward domain, BDD to define business scenarios, and TDD to implement the service logic safely.

## 3. “What is JUnit?”

JUnit is the main testing framework for Java. In Spring Boot projects, I use **JUnit 5** to define and run automated tests.

It provides annotations like:

```java
@Test
@BeforeEach
@AfterEach
@ParameterizedTest
```

A simple JUnit 5 test looks like this:

```java
@Test
void calculateReward_returnsExpectedPoints() {
    int points = rewardCalculator.calculate(120);

    assertThat(points).isEqualTo(90);
}
```

JUnit gives the structure for writing tests, running them through Maven or Gradle, and reporting pass/fail results. In CI/CD, Jenkins runs these tests automatically before packaging or deployment.

## 4. “What is Mockito?”

Mockito is a mocking framework for Java. I use it to isolate the class under test by replacing dependencies with mock objects.

For example, if my service depends on a repository, I do not want the unit test to hit a real database. I mock the repository and control its behavior.

```java
when(rewardRepository.findByCustomerId(1L))
        .thenReturn(Optional.of(customerReward));

verify(rewardRepository).save(any(Reward.class));
```

Mockito helps me test:

```text
What does the service return?
What exception does it throw?
Did it call the repository?
Did it avoid calling the repository when validation failed?
```

I use mocks for external dependencies, but I avoid mocking the class I am testing.

## 5. “How do you test your application?”

I test my application using a layered testing strategy.

First, I write **unit tests** for service-layer business logic. These are fast and isolated. I use JUnit 5, Mockito, and AssertJ.

Second, I write **controller tests** using `@WebMvcTest` and `MockMvc`. These verify REST endpoints, status codes, request validation, and JSON responses.

Third, I write **integration tests** using `@SpringBootTest`. These verify that the Spring context loads correctly and that the full request flow works.

Fourth, I add **regression tests** whenever I fix a bug. If a bug happens once, I write a test to make sure it does not happen again.

Fifth, I run everything in CI/CD. In Jenkins, the pipeline runs:

```text
Checkout
Test & Coverage
SonarQube Analysis
Quality Gate
Package
Docker Build
Deploy
```

I also use **JaCoCo** to measure coverage. In my recent project, the coverage requirement was 90% or above, so the Maven build fails if coverage drops below that threshold.

## 6. “What tools do you use for code quality analysis?”

For Java/Spring Boot projects, I usually use:

```text
JaCoCo for test coverage
SonarQube for bugs, vulnerabilities, code smells, duplication, and quality gates
JUnit reports in Jenkins for test results
Maven Checkstyle or PMD if the team requires style/static rules
IDE inspections for local feedback
```

```text

target/site/jacoco/jacoco.xml
```

Then Jenkins sends the JaCoCo XML report to **SonarQube**. SonarQube checks code quality and gives a Quality Gate result. This helps prevent low-quality code from being deployed.

## 7. “Authentication vs Authorization?”

**Authentication** answers the question: Who are you?

It verifies identity. Examples include username/password login, SSO, OAuth2 login, or validating a JWT.

**Authorization** answers the question: What are you allowed to do?

It controls access after the user is authenticated. For example, an admin can delete a reward rule, but a regular user can only view their own rewards.

A simple example:

```text
Authentication: User logs in successfully.
Authorization: System checks whether that user has ROLE_ADMIN before allowing access to /admin/rewards.
```

In Spring Security, authentication usually happens through filters and authentication providers. Authorization is usually enforced through roles, authorities, URL rules, or method-level annotations like:

```java
@PreAuthorize("hasRole('ADMIN')")
```

## 8. “Encryption vs Hashing vs Encoding?”

**Encoding** is not security. It just transforms data from one format to another so it can be stored or transmitted safely. For example, Base64 encoding. Anyone can decode it.

**Hashing** is one-way. You cannot reverse a hash back to the original value. It is commonly used for passwords. For passwords, we should use slow salted hashing algorithms like BCrypt, Argon2, or PBKDF2.

**Encryption** is two-way. You encrypt data using a key, and later decrypt it using a key. It is used when you need to recover the original value, such as sensitive data stored in a database.

So:

```text
Encoding = reversible formatting, not secure
Hashing = one-way, used for passwords/integrity
Encryption = reversible with a key, used for sensitive data
```

Example:

```text
Password storage → hashing with BCrypt
Credit card or SSN storage → encryption
API payload over network → TLS encryption
Binary-to-text transport → Base64 encoding
```

## 9. “How do you secure your application?”

I secure the application at multiple layers.

At the API layer, I use **Spring Security** to enforce authentication and authorization. Public endpoints are explicitly allowed, and protected endpoints require a valid token or session.

At the authentication layer, I usually use JWT or OAuth2 depending on the system. For internal APIs, JWT is common. For third-party login or delegated access, OAuth2 is more appropriate.

At the password layer, I never store plain-text passwords. I store only salted password hashes using BCrypt or a similar secure algorithm.

At the transport layer, I use HTTPS/TLS so data is encrypted in transit.

At the data layer, I protect sensitive data through encryption, least-privilege database users, and avoiding unnecessary sensitive data storage.

At the application layer, I validate input, handle exceptions safely, avoid exposing stack traces, use parameterized queries or JPA to prevent SQL injection, and configure CORS carefully.

At the CI/CD layer, I avoid hardcoding secrets. I store secrets in Jenkins credentials, environment variables, or a secret manager.

At the observability layer, I log enough information for debugging, but I avoid logging passwords, tokens, or sensitive personal information.

## 10. “What is JWT?”

JWT stands for **JSON Web Token**. It is a compact token format commonly used for stateless authentication.

A JWT has three parts:

```text
Header.Payload.Signature
```

The **header** contains metadata like the signing algorithm.
The **payload** contains claims, such as user ID, username, roles, issuer, and expiration time.
The **signature** proves that the token was issued by a trusted server and was not modified.

Example claims:

```json
{
  "sub": "user123",
  "roles": ["USER"],
  "iat": 1710000000,
  "exp": 1710003600
}
```

In a Spring Boot application, the client sends the token in the request header:

```http
Authorization: Bearer <jwt-token>
```

The server validates the signature and expiration, then creates an authenticated security context.

Important point: JWT is usually **signed**, not encrypted. Anyone can decode the payload if they have the token, so we should not put secrets or sensitive data inside the JWT.

## 11. “What is OAuth2?”

OAuth2 is an authorization framework that allows one application to access resources on behalf of a user without sharing the user’s password.

For example, when an application says:

```text
Login with Google
```

or

```text
Allow this app to access your GitHub profile
```

that is usually OAuth2 or OpenID Connect.

The main roles are:

```text
Resource Owner: the user
Client: the application requesting access
Authorization Server: issues tokens
Resource Server: API that protects the data
Access Token: token used to access protected resources
Refresh Token: token used to get a new access token
```

OAuth2 itself is mainly about authorization. For login/authentication, we usually use **OpenID Connect**, which is built on top of OAuth2 and adds an ID token.

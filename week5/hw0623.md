# Distributed Transactions (2PC & SAGA)

## 1. Why Distributed Transactions?

* **Monolithic Architecture:** Transactions are easy to handle. A single Spring Boot application connects to a single database. Using Spring's `@Transactional` annotation handles atomic operations (either all queries succeed or all fail) because they execute within the same JVM and same database.
* **Microservice Architecture:** Business flows are split across multiple independent services (e.g., Employee Service, Account Service, Audit Log Service), often running on different servers (different JVMs) with different databases. The standard `@Transactional` annotation cannot guarantee atomicity across different JVMs or separate database sources.
* **Solution:** We must use **Distributed Transaction** design patterns like 2PC or SAGA to ensure data integrity across microservices.

---

## 2. Two-Phase Commit (2PC) Pattern

The 2PC pattern introduces an independent **Coordinator** to synchronize and monitor the status of query executions across all involved microservices.

### How it Works (The Two Phases)

1. **Phase 1: Preparation (Prepare Phase)**
* The Coordinator asks all participating services if they are ready to execute their queries.
* The services do *not* execute the queries yet. Instead, they check if the execution is possible (e.g., checking DB connections, validating if records already exist, verifying no constraints are violated).
* Each service replies to the Coordinator with a "Yes" (executable) or "No" (failed).


2. **Phase 2: Execution (Commit/Rollback Phase)**
* If **ALL** services confirm they can execute (all say "Yes"), the Coordinator sends a commit signal to execute the SQL statements.
* If **ANY** service fails the preparation check, the request is stuck in the preparation stage and the Coordinator aborts the transaction. None of the queries are executed.



### Characteristics of 2PC

* **Consistency Model:** **Strong / Real-time Consistency**. All databases are updated simultaneously only when everything is guaranteed to succeed.
* **Implementation Example (Spring Boot):** * To implement across multiple database sources, you must exclude the default auto-configuration (`DataSourceAutoConfiguration`, `DataSourceTransactionManagerAutoConfiguration`).
* You can use third-party libraries like **Atomikos** to serve as the JTA (Java Transaction API) transaction manager (acting as the 2PC coordinator) across the different DataSources (e.g., your primary EMS database and secondary Audit database).


* **Drawbacks:**
1. **Latency / Bottleneck:** The transaction has to wait for the slowest service to finish the preparation phase.
2. **Single Point of Failure (SPOF):** If the Coordinator goes down, no distributed transactions can be executed. To mitigate this, companies must run a cluster of Coordinators behind a load balancer.

## 3. SAGA Pattern

The SAGA pattern is designed to shake off the centralized bottleneck of 2PC. Instead of preparing and waiting, services execute their transactions immediately. If a downstream step fails, the system runs **Compensation Logic** to undo the previous steps.

### Core Concepts

* **Compensation Logic:** For every SQL operation, there must be a corresponding reverse operation. If Step 1 was `INSERT`, the compensation is `DELETE`. If Step 1 was an `UPDATE`, the compensation reverts that update.
* **Consistency Model:** **Eventual Consistency**. Since step 1 commits immediately, there is a window of time where Step 1 is done, but Step 2 is not yet finished. The system is temporarily out of sync but will "eventually" become consistent (either by finishing the flow or rolling back everything).

### SAGA Styles

#### A. Choreography (Decentralized)

* **How it works:** Services communicate directly with each other, usually via events/messages (e.g., HTTP requests or a Kafka message queue).
* **Flow:** * Service 1 (S1) executes its query and publishes an event (e.g., `EmployeeCreatedEvent`).
* Service 2 (S2) listens for this event, executes its query, and triggers S3.


* **Rollback:** If S3 fails, it fires a failure event back to S2. S2 runs its compensation method, then fires a failure event to S1. S1 runs its compensation method.
* **Pros/Cons:** Highly decentralized, no single point of failure. However, no single service has the "big picture" of the whole business flow, making it harder to track complex transactions.

#### B. Orchestration (Centralized)

* **How it works:** A dedicated, centralized application (the **Orchestrator** or flow controller) manages the routing and logic of the business flow.
* **Flow:** * The user hits the Orchestrator.
* The Orchestrator tells S1 to execute. S1 succeeds and replies to the Orchestrator.
* The Orchestrator then tells S2 to execute. S2 succeeds and replies.
* If the Orchestrator tells S3 to execute and S3 fails, the Orchestrator takes over the rollback.


* **Rollback:** The Orchestrator inherently knows the state of the flow. It directly sends compensation requests back to S2, and then to S1.
* **Pros/Cons:** Much easier to maintain and update business flows because the logic is centralized in the Orchestrator, rather than scattered across dozens of individual services. Requires setting up a highly available Orchestrator cluster to prevent SPOF.

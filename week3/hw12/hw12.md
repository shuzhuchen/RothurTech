## 1. What Spring Boot version have you used?

I have used both Spring Boot 2.x and Spring Boot 3.x.

For Spring Boot 3, one important requirement is that the minimum Java version is Java 17. Another major change is the migration from `javax.*` packages to `jakarta.*` packages.

## 2. What annotations have you used in Spring?

Annotations I use are related to IoC, DI, AOP, and RESTful API design.

For IoC, the main annotation is `@SpringBootApplication`. It includes `@EnableAutoConfiguration`, `@Configuration`, and `@ComponentScan`.

For bean registration in a three-layer architecture, I use `@RestController` or `@Controller` for the controller layer, `@Service` for the service layer, and `@Repository` for the DAO layer. If a class does not clearly belong to controller, service, or repository, I can use `@Component`.

For third-party libraries where I do not control the source code, I usually use `@Configuration` on the configuration class and `@Bean` on the method to register the bean into the Spring container.

For bean scopes, I can use `@Scope`. Common scopes include singleton, prototype, request, session, and application. The default scope is singleton.

For dependency injection, I use `@Autowired`, and there are three injection styles: constructor injection, field injection, and setter injection. If there are multiple beans of the same type, I can use `@Qualifier` with the bean name to resolve the conflict.

For AOP, I have used `@RestControllerAdvice` and `@ExceptionHandler` for global exception handling. Another style is using `@Aspect`, `@Pointcut`, and annotations like `@Around`, `@Before`, `@After`, `@AfterThrowing`, and `@AfterReturning`.

For RESTful API design, I use `@RestController`, `@RequestMapping`, `@GetMapping`, `@PostMapping`, `@PutMapping`, and `@DeleteMapping`. For request input, I use `@RequestParam`, `@PathVariable`, `@RequestHeader`, and `@RequestBody`.

## 3. What is Enable Auto Configuration?

Enable Auto Configuration is a core feature of Spring Boot. When the application starts, Spring Boot checks the dependencies imported in Maven pom.xml. Based on the jar packages on the classpath, Spring Boot automatically loads the related configuration classes into the Spring container.

## 4. How do you stop auto configuration in Spring Boot?

one way is to use the exclude attribute inside @SpringBootApplication.

For example, I can write:

`@SpringBootApplication(exclude = {DataSourceAutoConfiguration.class})`

This tells Spring Boot not to load that specific auto-configuration class.

If needed, I can also exclude multiple auto-configuration classes. The key idea is that auto configuration is useful by default, but when some configuration does not fit my application, I can explicitly exclude it.

## 5. What are the advantages of Spring Boot Framework?

Spring boot framework has 4 main advantages.

The first advantage is auto configuration. Spring Boot can automatically configure components based on the dependencies I imported in Maven.

The second advantage is embedded Tomcat. I do not need to manually install Tomcat or deploy a WAR file. I can directly run the application using `java -jar`.

The third advantage is starter packages. For example, with `spring-boot-starter-web`, I do not need to manually import many different Maven coordinates. Spring Boot bundles the commonly used dependencies together.

Another advantage is Actuator. It provides built-in endpoints for health checks and monitoring.

Spring Boot also supports externalized configuration through `application.properties` or `application.yaml`. YAML is just another format. It is more structured, but the functionality is basically the same as properties. If it is a legacy application, using properties is fine. If it is a new application, YAML is also common.


## 6. How do you define Profile?

Spring Profile is used for environment segregation.

In projects, we usually have different environments, such as dev, QA, UAT, staging, and prod. Each environment may have different database URLs, credentials, API endpoints, and other configurations.

So the main purpose of Profile is not just to avoid hard coding. The more important purpose is to separate configurations for different environments.

For example, I can have `application.properties` as the default configuration and also have environment-specific files like `application-dev.properties`, `application-QA.properties`, or `application-prod.properties`.

When a profile is active, Spring Boot loads the default configuration first, and then loads the environment-specific configuration. If the same property exists in both files, the environment-specific one overrides the default value.

## 7. Why AOP?

AOP is Aspect-Oriented Programming. It's used to enhance functionality by breaking the normal serial execution flow. It allows us to add extra logic around the original method execution without changing the core code.

It also helps avoid duplicate code patterns. For example, logging, security checks, and exception handling may be needed in many places. Without AOP, we may need to repeat the same logic in many methods.

With AOP, we can centralize this cross-cutting logic in one place and apply it to multiple methods through pointcuts and advice.

In Spring, one style of AOP is `@RestControllerAdvice` with `@ExceptionHandler` for global exception handling. Another style is using `@Aspect`, `@Pointcut`, and advice annotations like `@Around`, `@Before`, `@After`, `@AfterThrowing`, and `@AfterReturning`.

## 8. What Java version can we use with Spring Boot 3?

Spring Boot 3 requires Java 17 as the minimum Java version.

Another related point is that Spring Boot 3 changed from `javax.*` packages to `jakarta.*` packages, so Java version compatibility and package migration are important when upgrading from Spring Boot 2 to Spring Boot 3.

## 9. What are the injection types in Spring?

There are three dependency injection types in Spring: constructor injection, field injection, and setter injection.

Constructor injection is the recommended one.

The reason is that constructor injection ensures all required dependencies are available when the application starts. If a required bean is not created properly, the application can fail fast during startup instead of causing a `NullPointerException` later at runtime. Constructor injection is also easier for unit testing because I can directly pass mock objects into the constructor.

Field injection is simple, but it hides the dependencies and makes testing harder.

Setter injection can be used when the dependency is optional.

Also, when doing dependency injection, there may be circular dependency issues. For example, bean A depends on bean B, and bean B depends on bean A. One way to break this is using `@Lazy`, so Spring delays the initialization until the bean is actually needed.

If there are multiple beans of the same type, Spring may have a type conflict. In that case, I can use `@Qualifier("beanName")` to specify which bean should be injected.

## 10. How do you implement exception handling in Spring Boot?

I would answer this in two parts: exception implementation and exception handling.

1. from the Java side, exceptions can be divided into checked exceptions and unchecked exceptions. Checked exceptions are compile-time exceptions, such as `IOException` or `SQLException`. Unchecked exceptions are runtime exceptions, such as `NullPointerException` or `IllegalArgumentException`.

2. for handling exceptions in Spring Boot, I usually use AOP-style centralized handling instead of writing try-catch logic in every controller method.

One common way is using `@RestControllerAdvice` with `@ExceptionHandler`. `@RestControllerAdvice` can intercept exceptions from the controller layer and return a consistent response format.

Another way is using `@Aspect` with `@Pointcut`, and advice annotations such as `@Around`, `@Before`, `@After`, `@AfterThrowing`, and `@AfterReturning`.

## 11. CompletableFuture and multithreading in Spring Framework

`CompletableFuture` is a Java 8 feature. It is an improvement over the old `Future` or `FutureTask`.

With traditional `Future`, when we need the return value, it may block the main thread. `CompletableFuture` provides more powerful chaining APIs, so we can run tasks asynchronously, combine results, and handle results more flexibly.

In a Spring Boot project, I usually use `CompletableFuture` in the service layer for parallel processing. For example, if I need to split data into multiple chunks, process them in parallel, and then combine the results, I can use `CompletableFuture.allOf()` to join them back and build the final response.

In Spring, I can also use `@Async` on a service method to execute it asynchronously. For example, I may have a method like `fetchUserAsync(Long id)` returning `CompletableFuture<User>`. If multiple requests call this method, Spring can execute them in parallel instead of one by one. To enable this, I need `@EnableAsync`, usually in a configuration class.

In production, I should not rely only on the default executor. I should configure a dedicated thread pool, usually using `ThreadPoolTaskExecutor`. A custom thread pool usually includes seven parameters: core pool size, max pool size, queue capacity, keep alive time, thread factory, rejection policy, and time unit.

We may also define multiple thread pools. For example, core business tasks such as order processing, payment, and financial operations should use a primary thread pool with more resources. Auxiliary tasks such as email notification, SMS notification, template generation, and monthly reports can use a smaller auxiliary thread pool. If the auxiliary pool is full, we can use a simpler rejection policy, such as discarding the oldest task in the queue. That way, auxiliary tasks may be delayed or discarded, but the core business operations are protected.

This topic also connects Java multithreading with Spring. Besides `CompletableFuture` and `@Async`, I should also understand CAS, such as `AtomicInteger` and `AtomicReference`, which are lock-free mechanisms. For thread-safe data structures, I can use `Collections.synchronizedList` or `ConcurrentHashMap`. For locking, I can use the `synchronized` keyword or the `Lock` interface, such as `ReentrantLock`.

In Java 21, virtual threads are also introduced. With virtual threads, we can handle large-scale concurrency in a lighter way, and in some cases we do not need to manually manage traditional thread pools as much as before.

## 12. What annotations do we use to configure customized Actuator?
For most projects, we usually do not customize Actuator too much. I usually expose existing Actuator endpoints like health, metrics, and prometheus, then connect them with Prometheus and Grafana.

If we really need to create a custom Actuator endpoint, we can use @Endpoint.

Inside the endpoint, we can use @ReadOperation for read-only operations, @WriteOperation for write operations, and @DeleteOperation for delete operations.

Actuator provides production-ready monitoring endpoints. Custom Actuator is more common for platform teams or logging/monitoring teams. For normal business service teams, we usually just configure and expose existing endpoints.


## 13. How does Spring IoC work? Include all annotations, injection, and bean types.

Spring IoC means Inversion of Control. In Spring Boot, the Spring container manages object creation, dependency injection, and bean lifecycle.

The starting point is usually the `@SpringBootApplication` annotation on the main class. This annotation includes `@EnableAutoConfiguration`, `@Configuration`, and `@ComponentScan`.

`@EnableAutoConfiguration` loads configurations based on the dependencies imported in Maven. `@Configuration` registers configuration classes. `@ComponentScan` scans classes with Spring annotations and registers them as beans in the Spring container.

For bean registration, in a normal three-layer architecture, I use `@RestController` or `@Controller` in the controller layer, `@Service` in the service layer, and `@Repository` in the DAO layer.

If a class does not belong to those layers but still needs to be managed by Spring, I can use `@Component`.

For third-party libraries where I cannot modify the source code, I use `@Configuration` on a configuration class and `@Bean` on a method to register that object into the Spring container. Examples include thread pools, database connection pools, or external SDK clients.

After beans are registered, Spring supports different bean scopes. The default scope is singleton, which means one bean instance per Spring application context.

Prototype means a new bean instance is created every time the bean is dependency injected.

Request scope means one bean instance is created for each HTTP request.

Session scope means one bean instance is created for each user session.

Application scope means one bean instance is created for each application context.

The implementation of IoC is dependency injection. Spring supports three injection types: constructor injection, field injection, and setter injection.

Constructor injection is the recommended approach because it ensures dependencies are ready when the application starts, prevents `NullPointerException`, and makes unit testing easier.

If multiple beans have the same type but different implementations, Spring may not know which one to inject. In that case, I use `@Qualifier("beanName")` to specify the exact bean.

So my structure for Spring IoC is: first, Spring Boot starts from `@SpringBootApplication`; second, it scans and registers beans using annotations like `@RestController`, `@Service`, `@Repository`, `@Component`, `@Configuration`, and `@Bean`; third, it manages bean scopes like singleton, prototype, request, session, and application; finally, it injects dependencies through constructor, field, or setter injection.

## 14. Could AOP apply to a private method?

No, Spring AOP cannot be applied to private methods. The reason is that Spring AOP is proxy-based. A proxy can intercept method calls by overriding or wrapping accessible methods, but a private method cannot be overridden by the proxy.

Also, even if there is a public method calling another method inside the same class, this self-invocation may bypass the Spring proxy, so the nested method may not be intercepted either.

The common solution is to extract that logic into another Spring bean and inject that bean back into the original class. Then the method call goes through the Spring proxy and AOP can work.

Another option is self-injection, but I need to be careful about circular dependency.

A more advanced option is AspectJ weaving, which is based on Java-level weaving instead of only Spring proxy-based AOP. But in normal Spring Boot projects, extracting the method into another Spring bean is the standard and cleaner approach.


## 15. How can you use Profile?

Spring Profile is used for environment segregation. In real projects, we usually have multiple environments, such as dev, QA, UAT, staging, and prod. Each environment has its own database URL, credentials, external service endpoints, and other configurations.

There are several ways to activate a profile.

The first way is in `application.properties`:

`spring.profiles.active=dev`

In YAML, it looks like:

`spring:
  profiles:
    active: dev`

The second way is through the command line when starting the application on a remote server:

`java -jar springboot.jar --spring.profiles.active=QA`

The third way is using environment variables on Linux:

`export SPRING_PROFILES_ACTIVE=QA`

After setting this environment variable, if I start the Spring Boot application in that terminal session, Spring Boot will read the active profile automatically.

When the QA profile is active, Spring Boot loads the default `application.properties` first and then loads `application-QA.properties`. If the same configuration key exists in both files, the value in `application-QA.properties` overrides the default one.

In local development with IntelliJ, I can also set the active profile in the run configuration. But on a remote server, I usually use command-line arguments or environment variables.

## 16. How do you customize an annotation in Java?

To customize an annotation, I use `@interface`.

For example:

`public @interface MyAnnotation { }`

When creating a custom annotation, the important part is using meta-annotations.

The most important ones are `@Target` and `@Retention`.

`@Target` defines where the annotation can be applied, such as class, method, or field.

`@Retention` defines when the annotation is still valid, such as source level, class loading level, or runtime level.

Other meta-annotations include `@Inherited`, which controls whether the annotation can be inherited by child classes, and `@Repeatable`, which allows the same annotation to be used multiple times at the same location with different values.

key idea: `@Target` defines where, and `@Retention` defines when.
